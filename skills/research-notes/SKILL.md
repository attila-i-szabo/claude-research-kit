# Research notes

Follow skill `research-writing` (standards, budgets, references, paper library), skill `project-layout` (where files go, README, cross-references) and skill `markdown-style`. This skill adds what is specific to notes that contain new results.

## Literature steps (required)

1. **Before starting your own derivations**, check what can already be inferred from existing reviews of the topic in the same root (skill `project-layout`, "Root"). If the topic is probably well treated in the literature and no review covers it, suggest to the user commissioning one (skill `research-review`) before deriving it from scratch.
2. **Before a notes file is finished**, run the `lit-searcher` agent on each new result or method of the file (one agent per file, with a list of the results; do not search per sentence). Download and read only papers that turn out to be decisive, using `paper-extractor` and the budgets of `research-writing`.
3. **Every nontrivial claim then either cites prior work** inline, or says "derived here; no prior reference found (searched: …)" with a short description of what was searched. Standard textbook facts get a textbook or review reference.
4. Notes may cite reviews in other directories of the same root (skill `project-layout`, "Cross-references") rather than repeating them, where that does not cost self-containedness of the argument.

## Derivations

- Every step of a derivation is written out to the standards of `research-writing` ("Rigour and clarity"). State assumptions where they enter.
- Mark clearly what is **derived here**, **cited**, and **genuinely open**. A result checked only numerically, or only in a limit, is labelled as such.
- **Check derivations numerically where cheap**: a script in `code/` that tests an identity on random inputs or a small case is worth writing. Say in the text which script checks which equation.
- Notation is defined once per file (or cited from another file of the directory by its cross-reference) and used consistently in the code (skill `python-style`).

## Notes about code and runs

- A notes file that designs code states the interface and the formulas implemented. The code's docstrings cite the notes by cross-reference instead of repeating the derivation (skill `python-style`).
- An analysis of a run states the configuration (code version or script, parameters, sizes, seeds, data path) precisely enough to reproduce it, then the numbers, then the interpretation. Keep the interpretation separate from the observations.
- Figures are generated by scripts in `code/`; the text names the script.
